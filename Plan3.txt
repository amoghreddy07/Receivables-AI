# FINAL IMPLEMENTATION BLUEPRINT — Vasooli: B2B Receivables Recovery Agent

Scope locked: **B2B overdue invoices + failed invoice payments + promise-to-pay**. No consumer subscriptions, mandates, voice, React, SSE, multi-agent, or elaborate stats. Real, runnable code; honest sandbox-vs-real-API separation; deterministic eval.

---

## 1. Product definition

**One line.** An agent for B2B finance teams that detects revenue at risk (overdue invoices, failed invoice payments), diagnoses *why* money isn't coming, proposes a bounded recovery playbook, and executes it through a policy engine — with LLM diagnosis firewalled from execution, deterministic compliance/fraud hard-stops, an append-only SHA-256 hash-chained audit trail, and measured recovery over a 40–50+ case seeded batch.

**Workflow (user = collections/revenue-ops lead).**
1. Dashboard opens on the **Recovery queue**: overdue invoices (days-overdue shown), failed invoice payments, tracked promises, each with ₹ at risk + risk score. Top bar shows **AUTONOMOUS/SUPERVISED** toggle.
2. Open a case → evidence timeline → diagnosis (root cause, confidence, evidence, LLM rationale or `DIAGNOSED_BY_RULES`) → proposed playbook vs. **policy verdict** (APPROVED / BLOCKED(reason) / REQUIRES_APPROVAL).
3. SUPERVISED: action sits **Pending Approval** with countdown; Approve / Decline(reason) audited; timeout → **auto-decline** (safe default). AUTONOMOUS: acts within policy.
4. Agent runs the playbook ladder: dunning reminder w/ payment link → smart retry → promise-to-pay follow-up → escalation. Recovered ₹ credited live.
5. Compliance (>120 days, DNC, bankruptcy) and fraud (AVS, 3× auth failure, fraud-lock) fire deterministically → hard stop + compliant escalation, never normal outreach.
6. Batch evaluation against seeded sandbox → recovery rate, ₹ recovered, precision, false-action rate, zero hard violations, vs NaiveRetryBaseline.

## 2. Architecture & the air gap

```
Razorpay webhooks (payment.failed, invoice.issued/paid/partially_paid,
                   payment_link.paid, order.paid)
        │  HMAC verify → dedup → normalize (idempotent)
        ▼
  ┌──────────────────────────── AGENT CORE ────────────────────────────┐
  │  DETECT → DIAGNOSE → DECIDE → EXECUTE → OBSERVE → AUDIT            │
  │  (hourly overdue-tick loop; event-driven otherwise)                │
  └───────┬───────────────┬─────────────────┬───────────────┬──────────┘
     detection/      diagnosis/(AI)     policy/(rules)   execution/
     risk score      rule classifier    engine           provider interface
     case lifecycle  + LLM (structured) compliance        ├─ RazorpayClient (real)
                     + fusion/fallback  fraud            └─ SeededSandbox (deterministic)
                     ✂ AIR GAP ✂        stopping rules
     diagnosis/ may NOT import execution/ or razorpay SDK (structural test)
```

**Dependency rules (enforced by `tests/test_air_gap.py`, AST import scan + runtime `sys.modules` check):**
- `diagnosis/` → imports shared schemas/enums + read-only case snapshots only. **No** `execution/`, **no** `razorpay`, **no** network client, **no** write capability.
- `policy/` → registry + rules + `ActionSpec` contracts. Never calls the LLM.
- `execution/` → consumes validated `ActionSpec` only.
- The LLM receives one redacted context snapshot and returns JSON. **No tools.** Policy engine is the only layer that produces side effects.

**Sandbox honesty:** `SeededSandbox` is the demo/eval provider: outcome = deterministic function `(case_id, scenario_label, attempt_count)`, seeded per case. It is NOT a real-payment claim — documented in README + docs/SANDBOX.md. `RazorpayClient` implements the same interface for real test-mode calls (payment links, invoices, payments fetch, signature verify) with a smoke-test script; real API availability never blocks the MVP.

## 3. AI component — diagnosis, fusion, fallback (deterministic contract)

- **Rule classifier (always available):** documented signal map (`docs/SIGNAL_MAP.md`) from Razorpay error codes/messages + case features → cause enum, with rule confidence.
- **LLM diagnoser (optional, env-gated):** one-shot structured JSON via function calling: `{root_cause, confidence, evidence[], recommended_playbook, rationale}` over a redacted context snapshot. No tools, no writes.
- **Fusion (exact semantics, unit-tested):** same cause → `fused = 0.5·rule + 0.5·llm`; act autonomously if `fused ≥ 0.65`; `0.5–0.65` → REQUIRES_APPROVAL; `<0.5` → escalate. Different causes → never auto-act → escalate with both stored.
- **LLM outage (connect error, timeout 8s + 1 retry, bad JSON):** case proceeds rule-diagnosed, flagged `DIAGNOSED_BY_RULES`. `--llm-mode rules` runs the whole system with the LLM removed — mandatory feature + demo moment.

## 4. State machine (complete transitions)

```
OPEN → DETECTED → DIAGNOSING → DECIDING
  → PENDING_APPROVAL ──approve──▶ EXECUTING        (supervised)
  │        └──decline / timeout-auto-decline──▶ CLOSED_DECLINED (audited)
  → EXECUTING (autonomous, approved by policy)
      → OBSERVING ──success──▶ RECOVERED (credit ₹, close)
      │           └──failure──▶ DECIDING (next ladder step) | STOPPED_RULE | ESCALATED
  → BLOCKED(reason) → STOPPED_COMPLIANCE | STOPPED_FRAUD | STOPPED_RULE | ESCALATED
  → CLOSED_NOOP (self-healed / low-risk / no-action)
```

Every transition writes an audit event. Pending interventions resume exactly-once via `interventions.status` + idempotency key (safe resume).

## 5. Data-driven playbook registry (`policy/playbooks.yaml`, validated at boot)

Schema per playbook: `name, applies_to_causes[], max_attempts, cooldown_hours, allowed_channels[], allowed_actions[], requires_human_gate, compliance_guards[]`.

| Playbook | Causes | Actions | Ladder/caps |
|---|---|---|---|
| `DUNNING_REMINDER` | overdue ≤120d, partial balance | send reminder + payment link (email/SMS enum, template id) | 3 reminders, 48h cooldown |
| `PAYMENT_LINK_RESEND` | failed payment, bounced reminder | create link (amount, 72h expiry) + notify | 1 link + 2 reminders |
| `SMART_RETRY` | technical failure, insufficient balance | re-attempt failed payment | max 2, ≥24h apart, 09:00–21:00 |
| `PROMISE_TO_PAY` | no-response, missed reminders (B2B only) | schedule follow-up on promised date | 2 follow-ups → escalate |
| `ESCALATE_HUMAN` | compliance, fraud, ladder exhausted, PTP broken, low confidence | enqueue w/ context + recommendation | human decides (audited) |

Refunds, discounts, amount edits, legal threats, off-channel contact: **not actions that exist.**

## 6. Policy engine — compliance, fraud, stopping rules (deterministic, tested)

- **Compliance (`policy/compliance_rules.py`):** `days_overdue > 120` (strict; tests at 120 allowed / 121 prevented, configurable `COMPLIANCE_MAX_DAYS=120`) → no normal actions, compliant escalation; `BANKRUPTCY` → cancel pending + escalate, zero outreach; `DNC`/`LEGAL_HOLD` → hard-stop all outreach, escalate. Rules evaluated before decision **and** again before dispatch.
- **Fraud (`policy/fraud_rules.py`):** AVS-mismatch signal, ≥3 consecutive auth failures in 7 days, or FRAUD_LOCKED/SUSPICIOUS_ACTIVITY code → hard STOP + ESCALATE, cancel pending, never retry, audit matched rule.
- **Stopping rules:** per-playbook max_attempts + cooldowns (from YAML); no-contact 21:00–09:00 customer-local; per-customer monthly cap; global daily budget; opt-out honored instantly.
- **Supervision:** default SUPERVISED; approval timeout `APPROVAL_TIMEOUT_MIN=30` → auto-decline + audit (`system-timeout`); human decisions audited with identity + reason.

## 7. Audit trail (hash chain) + verification demo

- Append-only `audit_events`: `seq, case_id, actor{system|agent_llm|policy|human}, action, payload JSON, hash=SHA-256(prev_hash‖canonical_payload), prev_hash`.
- Coverage: ingest, LLM call (model/redacted summary/output/tokens), fusion, policy verdict (matched/missed rules), dispatch + API request/response (redacted), outcomes, approvals/declines, escalations.
- Dashboard: **Verify Integrity** → green on intact chain; in `DEMO_MODE=1`, **"Tamper a row"** flips a payload → verification fails, offending row highlighted red. Same logic unit-tested offline.

## 9. Razorpay integration (real where practical, honest)

- Official `razorpay` SDK behind `PaymentProvider` interface. Real endpoints used (verified against docs): `POST /v1/payment_links` + `/notify` + `/cancel`, `GET /v1/payments`, `POST /v1/invoices` + `/issue` + `/notify`, webhook HMAC-SHA256 verification, event dedup.

## 10. Evaluation (40–50+ cases, deterministic, no hardcoded metrics)

- `scripts/generate_corpus.py` (seeded) → **~48 cases** in `data/eval_corpus/`: overdue 30/60/90 (10), **120/121 boundary (4)**, **DNC (3)**, **bankruptcy (3)**, partial balance (4), payment-failed-technical (6), payment-failed-insufficient-funds (5), **AVS (3), 3× auth failures (3), fraud-lock (3)**, PTP kept (3), PTP broken (3), **NO_ACTION negatives** (self-healed/low-risk, 6). Ground truth: `{correct_playbook|NO_ACTION, expected_recovered_amount, forbidden_actions, should_escalate}`.
- Harness replays the **real agent loop** against SeededSandbox; every run appends eval results + audit events. Metrics computed by `eval/metrics.py` from result rows: **recovery rate, ₹ recovered (actual & % of potential), precision@action, false-action rate, hard-violation count (asserted 0), escalation accuracy, per-playbook success, time-to-recover (simulated)**. Point metrics only. Baselines: **NaiveRetryBaseline** + RuleOnly. Reproducibility test: same seed → identical results.
- `tests/test_eval_zero_violations.py`: eval over compliance/fraud/stop-rule subsets → 0 hard violations.

## 11. Failure handling & tests (prioritized set only)

Duplicate webhook → dedup, single action · concurrent same-case events → no double action · failure-before-dispatch / mid-pipeline crash → exactly-once resume via idempotency key (sandbox call counts = 1) · LLM outage → rules fallback, pipeline continues · adapter 5xx → backoff 2/4/8s → PENDING_NETWORK, no duplicate charge · signature mismatch / stale events → drop + audit.

**Test suite:** `test_air_gap.py`, `test_compliance_boundary.py` (120/121, DNC, bankruptcy), `test_fraud_rules.py`, `test_fusion_fallback.py`, `test_stopping_rules.py`, `test_hashchain.py` (verify + tamper), `test_idempotency.py` (duplicates/concurrency/resume), `test_approval_timeout.py`, `test_eval_zero_violations.py`, `test_eval_reproducibility.py`, `test_sandbox_determinism.py`.
